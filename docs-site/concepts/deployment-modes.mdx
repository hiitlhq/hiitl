## Overview

hiitl supports three deployment modes. The mode is derived from the client's `api_key`, `evaluation` and `sync` settings, passed to the constructor or read from their `HIITL_*` variables — there is no separate mode flag. Both SDKs derive it by the same table.

| Mode | How to activate | Evaluator | Audit storage | Latency |
|------|----------------|-----------|---------------|---------|
| **Local** | No `api_key` | In-process | SQLite | In-process, no network hop |
| **Hybrid** (the default with a key) | `api_key` without remote evaluation (`server_url`, when given, is the sync target) | In-process, from policies synced from the hosted service | Local SQLite buffer, uploaded in batches | In-process, no network hop |
| **Hosted** | `api_key` + `server_url` + remote evaluation (`evaluation="remote"` / `evaluation: 'remote'`) | Server-side | PostgreSQL | One HTTP round trip |

## Local mode

Local mode runs everything in your process. No API key, no account, no hiitl server. Policies and routes are loaded from local files and audit records are written to an embedded SQLite database. The only network calls are to the sync routes you configure.

<CodeGroup>

```python Python
from hiitl import HIITL

# Zero-config — starts in OBSERVE mode
hiitl = HIITL()

# With a local policy file; mode="RESPECT_POLICY" makes it bind (the default OBSERVE_ALL observes)
hiitl = HIITL(
    agent_id="payment-agent",
    policy_path="./policies/payments.yaml",
    mode="RESPECT_POLICY",
)
```

```typescript TypeScript
import { HIITL } from '@hiitl/sdk';

// Zero-config — starts in OBSERVE mode
const hiitl = new HIITL();

// With a local policy file
const hiitl = new HIITL({
  agent_id: 'payment-agent',
  policy_path: './policies/payments.yaml',
  mode: 'RESPECT_POLICY',
});
```

</CodeGroup>

**When to use local mode:**
- Development and testing
- Single-process deployments
- Environments where you need zero network dependency
- Evaluating hiitl before committing to a hosted deployment

**What you get:**
- The evaluator runs in-process in your language
- Local SQLite audit trail
- No API key, no account, no infrastructure
- Full policy evaluation with all operators and conditions, and sync routes to your own endpoints

## Hosted mode

Hosted mode sends envelopes to the hiitl service for evaluation. Policies are managed via the API, and audit records are stored in PostgreSQL with team-wide visibility. It is an explicit opt-in: `evaluation="remote"` (Python) or `evaluation: 'remote'` (TypeScript), with `api_key` and `server_url`.

<CodeGroup>

```python Python
from hiitl import HIITL

hiitl = HIITL(
    agent_id="payment-agent",
    org_id="org_mycompany123456789",
    api_key="sk_live_abc123...",
    server_url="https://api.hiitl.com",
    evaluation="remote",
    signature_key="...",  # the API key's signing secret, shown when the key was created
)
```

```typescript TypeScript
import { HIITL } from '@hiitl/sdk';

const hiitl = new HIITL({
  agent_id: 'payment-agent',
  org_id: 'org_mycompany123456789',
  api_key: 'sk_live_abc123...',
  server_url: 'https://api.hiitl.com',
  signature_key: '...', // the API key's signing secret, shown when the key was created
  evaluation: 'remote',
});
```

</CodeGroup>

**When to use hosted mode:**
- Production deployments with multiple agents or services
- When you need centralized policy management
- When teams need shared audit visibility

**What you get:**
- Centralized policy management via API
- PostgreSQL audit storage, queryable by environment, agent, action and decision type
- Shared rate limit counters across distributed agents
- Team collaboration on policies and audit review

## Hybrid mode

Hybrid mode runs the evaluator locally and keeps it in step with the hosted service: policies are pulled on an interval (five minutes by default), audit records are uploaded in batches (every thirty seconds), and a disk cache lets the evaluator keep deciding when the service is unreachable, behind a circuit breaker. Routes are downloaded too but not yet applied by the SDK: a hybrid client asks only the routes in its own `routes_path`. A kill switch activated in the service is a new policy version: the SDK's kill-switch poll (every thirty seconds by default) sees the version change and pulls it in the same poll, and the version decides, never the switch list. This is the default mode when an API key is given.

**Cold start.** With no disk cache and no successful first sync, the default is to warn and continue in the client's own mode until a sync lands (`cache_status='empty'` on each decision): under `OBSERVE_ALL` every action is observed; under `RESPECT_POLICY` every action is blocked for want of a matching rule. `cold_start_behavior="fail-closed"` makes the Python constructor refuse to start, and the TypeScript client throw at its first `evaluate()`.

<CodeGroup>

```python Python
from hiitl import HIITL

hiitl = HIITL(
    agent_id="payment-agent",
    api_key="sk_live_abc123...",
    # api_key without evaluation="remote" is hybrid mode
)
```

```typescript TypeScript
import { HIITL } from '@hiitl/sdk';

const hiitl = new HIITL({
  agent_id: 'payment-agent',
  api_key: 'sk_live_abc123...',
  // api_key without evaluation: 'remote' is hybrid mode; server_url, when given, is the sync target
});
```

</CodeGroup>

**When to use hybrid mode:**
- You want local evaluation speed with policies managed centrally in the hosted service
- You want the evaluator to keep deciding when the service is unreachable

## How mode is auto-detected

The SDK determines the deployment mode from its resolved settings (constructor arguments, then `HIITL_*` variables):

```
No api_key provided?
  └─ Yes → LOCAL mode
  └─ No  → evaluation is remote?
              └─ Yes → HOSTED mode (server_url required, else ConfigurationError)
              └─ No  → HYBRID mode (sync=false forces LOCAL, key stored)
```

You never need to set a mode flag for local versus hybrid; hosted evaluation is an explicit opt-in.

## The evaluate() call is the same

Regardless of deployment mode, the `evaluate()` call looks identical. The mode only affects where evaluation happens and where audit records are stored.

<CodeGroup>

```python Python — same call in every mode
decision = hiitl.evaluate(
    "process_payment",
    parameters={"amount": 500, "currency": "usd"},
    target={"account_id": "acct_123"},
)

if decision.allowed:
    process_payment(...)
```

```typescript TypeScript — same call in every mode
const decision = await hiitl.evaluate({
  action: 'process_payment',
  parameters: { amount: 500, currency: 'usd' },
  target: { accountId: 'acct_123' },
});

if (decision.allowed) {
  await processPayment(...);
}
```

</CodeGroup>

## Migrating between modes

Moving from local to hosted is a constructor change, not a code rewrite. Your `evaluate()` calls, policy logic, and decision handling remain the same.

<Steps>
  <Step title="Start local">
    `HIITL()` with no arguments. Observe mode, zero config.
  </Step>
  <Step title="Add policies">
    `HIITL(policy_path="./policies/payments.yaml")` to evaluate against local policy files.
  </Step>
  <Step title="Move to hosted">
    `HIITL(api_key="sk_live_...")` for hybrid mode: policies managed centrally, evaluation still in-process. `HIITL(api_key="sk_live_...", server_url="https://api.hiitl.com", evaluation="remote")` for server-side evaluation.
  </Step>
</Steps>

## Outage behavior

In hosted mode, a request that cannot reach the service is retried with exponential backoff up to `max_retries`, and then `evaluate()` returns `CONTROL_PLANE_UNAVAILABLE`: not allowed under the default `fail_mode`, `FAIL_CLOSED`, and allowed with a warning under `FAIL_OPEN`. Either way the client records the call in its local store (`audit_db_path`) and sends the records the service could not take before its next call, once the service answers; while the breaker is open no call, and so no record, is sent. The hosted client holds a circuit breaker: after repeated outages it opens, and calls fail fast with `CIRCUIT_BREAKER_OPEN` until a reset interval passes and a probe is sent. In hybrid mode the evaluator keeps deciding from its cached policies, and the sync channel sits behind a circuit breaker that opens after repeated failures and probes again after a reset interval. In local mode there is no service to reach; a sync route that does not answer falls to the route's own `timeout_action`.
