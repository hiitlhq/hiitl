## The control point

hiitl is a single deterministic checkpoint that sits between an AI agent's decision and the actual execution of that action. Every action passes through `evaluate()` before anything happens in the real world.

```
Agent decides to act
        |
        v
  hiitl.evaluate()
        |
   +---------+
   | Policy  |
   | Engine  |
   +---------+
        |
   +----+----+
   |         |
ALLOW     BLOCK / PAUSE / ESCALATE ...
   |         |
Execute   Don't execute
```

The evaluation is deterministic: the same envelope and the same policy produce the same decision. Two inputs sit outside the envelope: the clock, for a rule's `valid_from` / `valid_to` window, and the SDK's rate-limit counters. There is no LLM inference, no probabilistic reasoning, and no model calls at decision time.

## The four internal planes

Every piece of hiitl code belongs to one of four internal planes.

<AccordionGroup>
  <Accordion title="SDK / Ingest Plane">
    Developer-facing SDKs that construct envelopes, submit them for evaluation, and return decisions. This is the integration surface — the code your application calls.
  </Accordion>
  <Accordion title="Decision Plane">
    The deterministic policy evaluation engine. Receives an envelope, evaluates it against the active policy set in precedence order, and returns a decision. Side-effect free — evaluation never mutates state.
  </Accordion>
  <Accordion title="Execution Plane">
    Optional adapters that execute or pass-through actions after an ALLOW decision. In most integrations, your application handles execution directly based on the decision.
  </Accordion>
  <Accordion title="Audit / Ops Plane">
    Audit logging, policy management, and observability. Each new evaluation of an admitted envelope produces an audit record where the store answers, including blocked actions. Each record carries a SHA-256 hash of its content.
  </Accordion>
</AccordionGroup>

## Evaluation flow

When your code calls `evaluate()`, here is what happens internally:

<Steps>
  <Step title="Envelope construction">
    The SDK first admits the supplied values, then builds a full [execution envelope](/concepts/envelope) from the minimal arguments you provide. A number outside the numeric domain is refused before an envelope exists, with no decision or record; the refusal names the field and its declared type and range, recommending text only where text is admitted. It fills in `org_id`, `agent_id`, `action_id` and the timestamp automatically, and an HMAC signature when you configure a `signature_key`.
  </Step>
  <Step title="Policy evaluation">
    The evaluator loads the active [policy set](/concepts/policies) and finds the rules that match. A matching `KILL_SWITCH` rule binds first, then a matching `BLOCK` rule, then any other matching rule. Within each, the highest priority wins; on a tie, the rule defined first. Under `RESPECT_POLICY`, an action no rule matches is blocked (`NO_MATCHING_RULE`). The SDK then applies any rate-limit window.
  </Step>
  <Step title="Audit record written">
    An [audit record](/concepts/audit-trail) is written for every evaluation — including blocked actions. If the audit write fails, the action is blocked: the decision is `BLOCK` with `error.code` `AUDIT_WRITE_FAILED`, in local, hybrid and hosted mode alike. Any other failure once the envelope exists is a decision too, recorded where the store answers: `BLOCK` with `error.code` `AUDIT_READ_FAILED` or `EVALUATION_FAILED` (see [error decisions](/concepts/decisions)).
  </Step>
  <Step title="Decision returned">
    A [decision object](/concepts/decisions) is returned with the outcome (`ALLOW`, `BLOCK`, `REQUIRE_APPROVAL`, etc.), reason codes, timing metadata, and the policy version used. Under the default `OBSERVE_ALL` mode, a decision that is not allowed comes back as `OBSERVE`, with the enforced decision in `would_be`. Your code inspects `decision.allowed` (or `decision.ok` in Python) and acts accordingly.
  </Step>
</Steps>

## Multi-language native evaluators

hiitl has native policy evaluators in both Python and TypeScript. These are not wrappers around each other — each is a full implementation in its target language.

<CardGroup cols={2}>
  <Card title="Python evaluator" icon="python">
    Runs in-process in your Python application. No subprocess, no Node.js dependency. Same evaluator powers both the SDK (local mode) and the hosted server.
  </Card>
  <Card title="TypeScript evaluator" icon="js">
    Runs in-process in your Node.js application. No Python dependency. Validated against the same conformance test suite as the Python evaluator.
  </Card>
</CardGroup>

Both evaluators are validated by a shared **conformance test suite** — a set of `(envelope, policy, expected_decision)` tuples defined in JSON. If the two evaluators ever disagree on a decision, the spec is right and the divergent implementation has a bug.

## Deployment modes

hiitl supports three deployment modes, auto-detected from how you construct the client. The two SDKs read the same options differently:

| Mode | Config | Evaluator | Audit | Latency |
|------|--------|-----------|-------|---------|
| **Local** | No `api_key` | In-process | SQLite | Sub-millisecond |
| **Hosted** | `api_key` + `server_url` + remote evaluation (`evaluation="remote"` / `evaluation: 'remote'`) | Server-side | PostgreSQL | Low tens of ms |
| **Hybrid** | `api_key`, with or without `server_url` (the sync target) | In-process | Local + sync | Sub-millisecond |

Learn more in [Deployment Modes](/concepts/deployment-modes).

## What hiitl does not do

hiitl is connective infrastructure. It does not replace the AI ecosystem — it gives the ecosystem a deterministic enforcement layer.

- **Does not orchestrate.** hiitl does not decide what agents should do or coordinate multi-step workflows.
- **Does not use LLMs at decision time.** The decision plane is deterministic. No model inference during evaluation.
- **Does not compete with observability tools.** Observability platforms detect. hiitl enforces. They work together via structured event emission.
