## What gets recorded

Every evaluation writes one audit record: allowed, blocked, observed, rate-limited, routed, or returned for a person. An envelope that fails validation, a signature that does not verify, or a policy that cannot be loaded or evaluated is answered with its error decision (`VALIDATION_ERROR`, `SIGNATURE_INVALID`, `POLICY_ERROR`), and that decision is recorded too. A request with no valid API key, insufficient scope, or a body that is not an envelope at all leaves no record. A body outside the numeric domain is not yet an envelope: after key and scope checks, the service returns a located 422 naming the field and its declared type and range, recommending text only where text is admitted. Even when that body carries a string `action_id`, this refusal leaves no audit record. When the record itself cannot be written, the answer is `BLOCK` with `AUDIT_WRITE_FAILED`, and nothing runs.

Each record carries:

| Field group | Contents |
|---|---|
| **Identifiers** | `event_id`, `org_id`, `environment`, `agent_id`, `user_id`, `action_id` |
| **The envelope** | the envelope as the integrating system built it, with each declared field stored as `[REDACTED]` and, through the gateway, each argument not declared recorded stored as its SHA-256 hash ([Data handling](/security/data-handling#redaction)) |
| **The decision** | the decision type, `allowed`, the reason codes, the matched rules, `policy_version`, and for `OBSERVE` the `would_be` decision with its reason codes |
| **Routes asked** | for each route the evaluation asked: the rule, the route, the outcome (`answered`, `failed_open`, `unanswered`), the names of the fields sent, any error |
| **Timing** | `ingest_ms`, `evaluation_ms`, `total_ms` |
| **Content hash** | SHA-256 over `event_id`, the canonical envelope and the canonical decision (RFC 8785) as stored, then `execution_result`, `redaction` and `review` where the record carries them, the same bytes in both SDKs and the hosted service |
| **Event type** | `action.evaluated`, or `signature.invalid` / `control_plane.unavailable` for those two decisions: computed from the decision each time the record is read or uploaded, never stored |

An action's records make its lifecycle: its decision, then the result of running it. `record_result()` / `recordResult()` and `POST /v1/actions/{action_id}/result` write the result as a new record carrying `execution_result`, against the action's latest decision, its content hash covering the result. They refuse a result for an action that was not allowed (a decision held for review takes one once its review lets it run) or a second, different one. An SDK's local store holds no review case: a result for a held decision is written there naming the review it did not read (`review`), and the service reads the case when the record is uploaded, refusing it when the case did not let the action run. In hosted mode, while the service cannot be reached, the SDK holds the result in its local store and sends it before the next call. See [Recording the result](/sdk/python-evaluate#recording-the-result) and [the API](/api/evaluate#recording-the-result).

## Append-only

The SDK writes a record once and never changes its content or deletes it. In hybrid mode it marks a record as uploaded once the service has accepted it. The hosted service exposes no endpoint that updates or deletes a record.

<Warning>
In the hosted service the audit write is awaited before the decision is returned; if the write fails, the request fails and the action does not proceed. hiitl does not return a decision without a record of it.
</Warning>

## Storage

<Tabs>
  <Tab title="Local and hybrid mode">
    Records are written to an embedded **SQLite** database in the agent's process. No external infrastructure is required.

    - File location is configurable (`audit_db_path`; the default is `./hiitl_audit.db` in the working directory)
    - In hybrid mode the file is also the upload buffer: records are uploaded to the service in batches and marked as uploaded
    - Query it with the SDK's audit queries or any SQLite client
  </Tab>
  <Tab title="Hosted mode">
    Records are stored in **PostgreSQL** by the service.

    - Indexed by `action_id`, `org_id`, `envelope_hash` and creation time
    - Row-level security on the audit tables: a tenant request reads only its own organization's rows
    - Retention is not applied by the service; records stay until removed under the service's terms
    - A record the service could not take (an outage's decision, a result recorded during one) is held in the client's own SQLite store (`audit_db_path`) and sent, oldest first, before its next call
  </Tab>
</Tabs>

## Security and tamper detection

### Content hashing

Every record carries a SHA-256 content hash of its own content. Recompute it from the stored row to detect a change to the row since it was written.

### Policy change record

In the hosted service every policy version carries a SHA-256 content hash, and each new version records when it was created and what changed: each rule added or removed, by name, and each changed field of a rule or of the set, before and after (see [List policy changes](/api/policies#list-policy-changes)). Every change record (a policy version, a route, an API key, the principal verifier, the redaction policy) names who made it in `changed_by` and the kind of caller in `actor_type`, read from the credential: `api_key`, `human` (a dashboard session), or `system` (a write the service makes itself, such as the onboarding default or an automatic rollback).

### Envelope hash in decisions

In hosted mode the decision response includes `envelope_hash`, a SHA-256 hash of the evaluated envelope, so the caller can confirm that what the service evaluated is what it sent. In local and hybrid mode the field is not set.

## Querying the audit trail

In local and hybrid mode, query the SQLite file: the Python SDK offers `query_by_org()` and `query_by_action_id()`; the TypeScript SDK offers `queryAudit()`.

A record names its action `action`, as its envelope does. Before record format 2.0 it was `tool_name`: a local store written before then renames its column when it opens, keeping each record, its hash and its sync mark.

In the hosted service, `GET /v1/audit` returns pages of up to 500 records, filtered by `environment`, `agent_id`, `action` and `decision_type`; `GET /v1/audit/{event_id}` returns one record. Both need the `read` scope.

## Taking records elsewhere

Records leave through the query API, the SQLite file, a database dump, or an outbound route. On the hosted service, each record the service writes, evaluated there or uploaded by a hybrid-mode SDK, is sent to every [outbound route](/configuration/routes#outbound-routes) whose filters it passes, as the audit API reads it, and retried on failure. A pure-local SDK delivers to no outbound route, and there is no OpenTelemetry export; see [Limits and roadmap](/reference/limits-and-roadmap).
