## What is a policy?

A policy is a versioned, deterministic rule set evaluated against envelope fields. Policies are the configuration surface for hiitl — they define what gets allowed, blocked, escalated, or rate-limited.

Policies are code. They are versioned, testable and reviewable, and the hosted service never changes a version once it is deployed.

## Structure

Policies are organized into **policy sets** — named collections of rules scoped to an organization and environment.

```yaml Policy set structure
policy_set:
  name: "payments-policy"
  version: "v2.1.0"
  description: "Payment processing controls for production"
  scope:
    org_id: "org_mycompany123456789"
    environment: "prod"

  rules:
    - name: "kill-switch-all-payments"
      # ... rule definition
    - name: "block-high-value"
      # ... rule definition
    - name: "allow-payments"
      # ... rule definition
```

On the hosted service, a policy set is stored and served per organization and environment. In a policy file, the set's `scope` is a label. To limit a rule to certain environments, agents or users, give the rule its own `scope` (see [Rule fields](#rule-fields)).

Both loaders accept a file with or without the top-level `policy_set:` key.

## Rules

A rule is the atomic unit of policy. Each rule has conditions (when does it apply?) and a decision (what outcome does it produce?).

```yaml Example rule
- name: "require-approval-high-value"
  description: "Require approval for payments over $500"
  priority: 100
  conditions:
    all_of:
      - field: "action"
        operator: "equals"
        value: "process_payment"
      - field: "parameters.amount"
        operator: "greater_than"
        value: 500
  decision: "REQUIRE_APPROVAL"
  reason_code: "HIGH_VALUE_PAYMENT"
```

### Rule fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | Unique rule identifier within the policy set |
| `description` | string | Yes | Human-readable explanation |
| `priority` | integer | Yes | Order within a decision class. Higher number wins (see [Priority and evaluation order](#priority-and-evaluation-order)) |
| `conditions` | object | Yes | Condition tree (see below) |
| `decision` | string | Yes | Decision outcome: `ALLOW`, `BLOCK`, `REQUIRE_APPROVAL`, `PAUSE`, `SANDBOX`, `KILL_SWITCH`, `ESCALATE`, `ROUTE`, `RATE_LIMIT`. Any other value is refused, naming the rule. A rule never writes `OBSERVE`: to observe a rule, stage it |
| `reason_code` | string | Yes | Machine-readable reason returned in the decision |
| `lifecycle_stage` | string | No | `"active"` (default), `"staged"`, `"draft"`, `"disabled"` or `"archived"`. See [Lifecycle stages](#lifecycle-stages-observe-before-you-enforce). |
| `scope` | object | No | Limits the rule to listed `agents`, `users` or `environments` (`dev`, `stage`, `prod`), or to a `percentage` of matching envelopes |
| `valid_from` / `valid_to` | string | No | ISO 8601 timestamps. Outside this window the rule is skipped |
| `route` | string | No | Route name for escalation decisions (`REQUIRE_APPROVAL`, `PAUSE`, `ESCALATE`) and for `ROUTE` |
| `remediation` | object | No | Structured guidance returned when the rule binds a decision that is not allowed, such as `BLOCK`. See [Remediation](#remediation) |
| `rate_limit` | object | No | `RATE_LIMIT` rules only: the window the rule meters, `{ limit, window_seconds, scope }`. See [Rate-limit rules](#rate-limit-rules) |
| `tests` | array | No | Envelopes the rule ships with and the decision each must get (`[{ envelope, expect }]`) |
| `observation_window_days` | integer | No | For staged rules: how long to observe before a regression report. Defaults to `7` |
| `metadata` | object | No | Additional data (SLA, reviewer info, etc.) |

hiitl's own tools also write lineage fields (`suggested_by`, `requirement_citation`, `waits_on`) on the rules they generate.

<Warning>
A policy is refused when it loads if a rule or the set carries a field the policy format does not define. Rules written for hiitl 0.1 used `enabled` and `mode`; both keys are now refused. Replace `enabled: false` with `lifecycle_stage: "disabled"`, delete `enabled: true`, and replace `mode: "observe"` with `lifecycle_stage: "staged"`.
</Warning>

## Conditions

Conditions determine when a rule applies. They support field references with dot notation, comparison operators, and logical composition.

### Logical operators

**`all_of`** (AND) — all conditions must be true:

```yaml
conditions:
  all_of:
    - field: "action"
      operator: "equals"
      value: "process_payment"
    - field: "environment"
      operator: "equals"
      value: "prod"
```

**`any_of`** (OR) — at least one condition must be true:

```yaml
conditions:
  any_of:
    - field: "sensitivity"
      operator: "contains"
      value: "money"
    - field: "sensitivity"
      operator: "contains"
      value: "irreversible"
```

**`none_of`** (NOT) — none of the conditions may be true:

```yaml
conditions:
  none_of:
    - field: "environment"
      operator: "equals"
      value: "dev"
```

### Comparison operators

| Operator | Types | Description |
|----------|-------|-------------|
| `equals` | all | Exact match (case-sensitive for strings) |
| `not_equals` | all | Not equal |
| `greater_than` | number | Numeric `>` comparison |
| `greater_than_or_equal` | number | Numeric `>=` comparison |
| `less_than` | number | Numeric `<` comparison |
| `less_than_or_equal` | number | Numeric `<=` comparison |
| `contains` | string, array | Substring match or array element membership |
| `not_contains` | string, array | Inverse of `contains` |
| `starts_with` | string | String prefix match |
| `ends_with` | string | String suffix match |
| `matches` | string | Regex match |
| `in` | all | Value is in a set (right-hand side is an array). An array on the left matches when every element is in the set |
| `not_in` | all | Value is not in a set. An array on the left matches when not every element is in the set |
| `exists` | all | Field exists in the envelope (value is `true` or `false`) |
| `conforms_to` | object | The field's value is an object that fits a parameter schema: `{ type: "object", properties, required, additionalProperties }` |

A condition on a field the envelope does not carry is false, for every operator except `exists`.

In place of a literal `value`, a condition can compare against another envelope field with `{"$field": "<path>"}`. For example, `value: {"$field": "parameters.limit"}` compares with the action's own `limit` parameter. A field reference has exactly one key. `$field`, `$declared` and `$uncalibrated` are reserved in policy values: a sibling key or a position that does not read the form makes the policy refuse at load. A caller’s own envelope data keeps these keys as data.

### Field path syntax

Use dot notation for nested envelope fields:

| Field path | Envelope location |
|------------|-------------------|
| `action` | Top-level `action` field |
| `parameters.amount` | `envelope.parameters.amount` |
| `target.account_id` | `envelope.target.account_id` |
| `cost_estimate.dollars` | `envelope.cost_estimate.dollars` |
| `sensitivity` | Array field (use `contains` operator) |
| `external.<source>.<field>` | Not the envelope: the answer a sync route returned during this evaluation |

### Nested conditions

Logical operators can be nested for complex rules:

```yaml
conditions:
  all_of:
    - field: "environment"
      operator: "equals"
      value: "prod"
    - field: "action"
      operator: "equals"
      value: "process_payment"
    - any_of:
        - field: "parameters.amount"
          operator: "greater_than"
          value: 10000
        - all_of:
            - field: "parameters.amount"
              operator: "greater_than"
              value: 1000
            - field: "confidence"
              operator: "less_than"
              value: 0.8
```

This reads: must be in prod AND must be process_payment AND (amount > $10,000 OR (amount > $1,000 AND confidence < 0.8)).

## Priority and evaluation order

Among the rules that match, one rule binds and produces the decision. A matching `KILL_SWITCH` binds first, then a matching `BLOCK`, then a rule of any other decision. Within each of those classes the higher `priority` binds, then the rule defined first.

When you enforce (`mode="RESPECT_POLICY"`), an action no rule matches is blocked with `NO_MATCHING_RULE`. Give the actions you want to let through an `ALLOW` rule.

The priority ranges below are a naming convention for authors. Precedence does not depend on them:

| Priority range | Category |
|----------------|----------|
| 1000+ | Kill switches |
| 900 - 999 | Deny / Block rules |
| 500 - 899 | Rate limits |
| 400 - 499 | Scope enforcement |
| 100 - 399 | Threshold checks |
| 50 - 99 | Approval requirements |
| 1 - 49 | Allow rules (default) |

<Warning>
**DENY always wins.** If an active rule that matches produces a `BLOCK` or `KILL_SWITCH`, that rule binds, whatever the priority of a rule that would allow. This is not configurable. Under the default `OBSERVE_ALL` mode, the call still returns `OBSERVE`, with the block in `would_be`.
</Warning>

## Lifecycle stages: observe before you enforce

Every rule has a `lifecycle_stage`, `"active"` by default. Set it to `"staged"` to see what a rule would do without enforcing it.

| Stage | What the evaluator does |
|-------|-------------------------|
| `active` | Evaluates the rule. Its decision can bind |
| `staged` | Evaluates the rule. It never binds; when it matches, it is recorded in `staged_observations` |
| `draft` | Skips the rule |
| `disabled` | Skips the rule. Use it to turn a rule off, such as a kill switch you are not using |
| `archived` | Skips the rule |

```yaml
- name: "block-high-value"
  description: "Payments over $10,000 would be refused"
  lifecycle_stage: "staged"   # observe what the rule would do; it does not bind
  priority: 900
  conditions:
    all_of:
      - field: "parameters.amount"
        operator: "greater_than"
        value: 10000
  decision: "BLOCK"
  reason_code: "AMOUNT_EXCEEDS_LIMIT"
```

When a staged rule matches, the decision comes from the active rules, and `staged_observations` shows what the staged rule would have done:

```python
decision.decision             # "ALLOW" (from an active allow rule)
decision.staged_observations  # [StagedObservation(rule_name='block-high-value',
                              #   policy_set='payments-policy', priority=900,
                              #   would_be_decision='BLOCK',
                              #   would_be_reason_codes=['AMOUNT_EXCEEDS_LIMIT'],
                              #   would_be_binding=True)]
```

Staging is per rule. To observe a whole policy, use the SDK's default mode, `OBSERVE_ALL`: a call the policy would refuse returns `OBSERVE` with `allowed: true`, and `would_be` shows the enforced decision. A call the policy allows returns `ALLOW`.

Writing a policy to the hosted service stages it. A rule written `active` that is not already active, unchanged, lands `staged` until it passes the promotion gate, and an edit to a staged or active rule lands beside it as its refinement. See [Create policy](/api/policies#create-policy).

## Remediation

A rule that refuses an action, such as a `BLOCK` rule, can include a `remediation` object with structured, actionable guidance.

```yaml
- name: "block-high-value-payments"
  description: "Payments over $10,000 are refused"
  priority: 900
  conditions:
    all_of:
      - field: "parameters.amount"
        operator: "greater_than"
        value: 10000
  decision: "BLOCK"
  reason_code: "AMOUNT_EXCEEDS_LIMIT"
  remediation:
    message: "Payment amount exceeds the $10,000 limit."
    suggestion: "Reduce amount to $10,000 or below, or request approval."
    type: "threshold"
    details:
      threshold: 10000
      max_allowed: 10000
```

When this rule binds under `RESPECT_POLICY`, the [decision response](/concepts/decisions) includes the `remediation` object as written, except the details that state a fact of the call, which are computed from it: `blocked_fields` written as `{ref, filter}` (the call's values at `ref` that are in `filter`), a threshold's `current_value` (the call's value at `field`) and a temporal `current_time` (the call's timestamp). An AI agent reading the response can use `remediation.details` to self-correct and retry.

`message`, `suggestion` and `type` are required. `type` is one of `field_restriction`, `threshold`, `scope`, `rate_limit`, `temporal` or `custom`.

## Rate-limit rules

A `RATE_LIMIT` rule with a `rate_limit` window meters the calls it matches:

```yaml
- name: "limit-refunds"
  description: "At most 20 refunds an hour per agent"
  priority: 600
  conditions:
    field: "action"
    operator: "equals"
    value: "issue_refund"
  decision: "RATE_LIMIT"
  reason_code: "REFUND_RATE"
  rate_limit:
    limit: 20
    window_seconds: 3600
    scope: "agent"   # action (default), agent, user, org or user_action
```

A windowed rate-limit rule does not bind. The decision comes from the other rules. When that decision is `ALLOW`, the SDK reads every matching window before it counts any. If one is over its limit, the call returns `RATE_LIMIT` with reason code `RATE_LIMIT_EXCEEDED`: `matched_rules` names the rule, `rate_limit` carries that window's counter state, and `remediation` is the rule's own. The call is counted in no window. Otherwise it is counted in every window, and the `ALLOW` carries the counter state of the window nearest its limit. Under `OBSERVE_ALL` nothing is blocked: a call past a limit returns `OBSERVE` with `would_be: RATE_LIMIT`, and the counters count what enforcing would count. A limiter that fails never lets the call through: the decision is `BLOCK` with `RATE_LIMIT_SERVICE_ERROR`. The SDK keeps its counters in memory.

## Full example

```yaml Complete policy set
policy_set:
  name: "payments-policy"
  version: "v2.1.0"
  description: "Payment processing controls for production"
  scope:
    org_id: "org_mycompany123456789"
    environment: "prod"

  rules:
    - name: "kill-switch-all-payments"
      description: "Emergency stop for all payments"
      lifecycle_stage: "disabled"   # set to "active" to stop every payment
      priority: 1000
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
      decision: "KILL_SWITCH"
      reason_code: "KILL_SWITCH_ACTIVE"

    - name: "block-suspended-agents"
      description: "Block payments from suspended agents"
      priority: 900
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
          - field: "agent_id"
            operator: "in"
            value: ["agent-123", "agent-456"]
      decision: "BLOCK"
      reason_code: "AGENT_SUSPENDED"

    - name: "require-approval-high-value"
      description: "Require approval for payments over $500"
      priority: 100
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
          - field: "parameters.amount"
            operator: "greater_than"
            value: 500
      decision: "REQUIRE_APPROVAL"
      reason_code: "HIGH_VALUE_PAYMENT"
      route: "finance-review"

    - name: "allow-payments"
      description: "Default allow for payments"
      priority: 10
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
      decision: "ALLOW"
      reason_code: "PAYMENT_ALLOWED"
```

Enforced with `mode="RESPECT_POLICY"`, this set returns:

- a $150 payment: `ALLOW`, `PAYMENT_ALLOWED`;
- a $2,500 payment: `REQUIRE_APPROVAL`, `HIGH_VALUE_PAYMENT`, with `route_ref` `finance-review`;
- any payment from `agent-123`: `BLOCK`, `AGENT_SUSPENDED`;
- an action the set does not mention, such as `send_email`: `BLOCK`, `NO_MATCHING_RULE`.

<Note>
**JSON is the primary format.** Policies are JSON objects internally. YAML is a convenience layer for humans — YAML files are parsed and converted to JSON before evaluation.
</Note>

## Versioning

- Every policy set carries a `version` string. Semver, such as `v2.1.0`, is the convention.
- On the hosted service, a deployed version is never changed, only superseded by a new version. A change deployed under a version string already in use gets the next unused string.
- Rollback means **deploying a previous version again**, not editing the current one.
- Every [decision](/concepts/decisions) includes the policy version used, enabling replay and debugging.
