Kill switches are the highest-precedence enforcement mechanism in hiitl. They are `KILL_SWITCH` rules within policies that stop every matching action while the rule is active.

## When to use kill switches

- **Active incident** -- Fraudulent activity, compromised credentials, data breach in progress
- **Runaway agent** -- Agent executing unintended actions at scale
- **Regulatory halt** -- Compliance requires immediate cessation of specific operations
- **Deployment rollback** -- New agent behavior is causing harm, need instant stop

## How kill switches work

Kill switches are regular policy rules with `decision: "KILL_SWITCH"`. Precedence is deny-wins: a matching active `KILL_SWITCH` rule binds before any `BLOCK` rule, and a `BLOCK` rule before any other decision, whatever their priorities. Priority orders rules within the same class.

- `lifecycle_stage: active` (the default) -- the rule binds. In hosted mode, and in an SDK constructed with `mode="RESPECT_POLICY"`, a matching action returns `KILL_SWITCH` with `allowed: false`. Under the SDK's default mode, `OBSERVE_ALL`, it comes back `OBSERVE` with `would_be: KILL_SWITCH`, so run an SDK that must honour kill switches under `RESPECT_POLICY`.
- `lifecycle_stage: disabled` -- the rule is skipped and other rules evaluate normally

No separate tables, models, or evaluation logic. Toggle the rule's `lifecycle_stage` within existing policy infrastructure.

## Local mode

Edit the policy file directly:

```yaml
name: payments
version: "v1.0.0"
description: "Payment kill switches for local mode"
scope:
  org_id: "org_devlocal0000000000"
  environment: "dev"
rules:
  - name: kill-switch-payments
    description: Stop all payments during an incident
    priority: 1000
    lifecycle_stage: active   # Toggle this: active or disabled
    conditions:
      all_of:
        - field: action
          operator: equals
          value: process_payment
    decision: KILL_SWITCH
    reason_code: KILL_SWITCH_PAYMENTS

  - name: allow-payments
    description: Allow payments
    priority: 50
    conditions:
      field: action
      operator: equals
      value: process_payment
    decision: ALLOW
    reason_code: PAYMENT_ALLOWED
```

In local mode (no `api_key`), the SDK's mtime-based caching detects the file change on the next `evaluate()` call. No restart needed.

## Hosted mode

### List kill switches

```bash
curl -H "Authorization: Bearer $API_KEY" \
  https://api.hiitl.com/v1/kill-switches
```

### Activate a kill switch

```bash
curl -X POST \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "Fraud detected in payment processing"}' \
  https://api.hiitl.com/v1/kill-switches/kill-switch-payments/activate
```

### Deactivate a kill switch

```bash
curl -X POST \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "Incident resolved, payments safe to resume"}' \
  https://api.hiitl.com/v1/kill-switches/kill-switch-payments/deactivate
```

### Verify via audit trail

```bash
curl -H "Authorization: Bearer $READ_API_KEY" \
  https://api.hiitl.com/v1/policies/changes
```

Look for `change_type: "KILL_SWITCH_ACTIVATED"` or `"KILL_SWITCH_DEACTIVATED"` in the most recent entries. Each record's `changed_by`, and the kill switch's `activated_by` or `deactivated_by`, is the API key that made the call (its `key_id`), read from the key the service authenticated. The request does not name it: a body carrying `activated_by` or `deactivated_by` is refused with `422`, naming the field.

### When the change takes effect

Activating or deactivating saves a new version of the active policy for the API key's org and environment.

- **Hosted evaluation** (`POST /v1/evaluate`) reads the active policy on every call, so it applies the change from the next evaluation.
- **An SDK in hybrid mode** evaluates in-process against the policy version it has synced. Its kill-switch poll, every 30 seconds by default, reads the active version and the switches it makes live, each with its rule; when that version is not the one the SDK has, it pulls it in that poll (a switch edited under its own name is a new version too). Until that pull lands, the SDK reads each call against the poll's switches first: a call a switch stops is `KILL_SWITCH` under the new version; where the policy sets `on_missing: fail_closed`, a call that lacks a field a switch reads is `BLOCK` with `MISSING_FIELD`, naming the field, under the new version; and every other call is decided by the version the SDK has. So a switch binds from the first evaluation after the poll, even while the pull fails; the pull is retried at every poll, and each failure is logged at error. The switch list alone decides nothing: a switch stops what its rule names. Set `kill_switch_poll_interval` in the sync configuration (or `HIITL_SYNC_KS_INTERVAL`) to poll more often; the minimum is 5 seconds.
- **An SDK in local mode** reads its policy file. Toggle the rule in the file, as above.

## Common scenarios

### Scenario 1: Emergency payment stop

<Steps>
  <Step title="Alert detected">
    Fraudulent transactions detected via monitoring.
  </Step>
  <Step title="Activate kill switch">
    `POST /v1/kill-switches/kill-switch-payments/activate`
  </Step>
  <Step title="Verify">
    Hosted payment evaluations return `KILL_SWITCH` with `allowed: false` from the next call. Hybrid SDKs running under `RESPECT_POLICY` do so from the first call after their next kill-switch poll.
  </Step>
  <Step title="Investigate">
    Identify root cause using the audit trail.
  </Step>
  <Step title="Fix and verify">
    Resolve the underlying issue.
  </Step>
  <Step title="Deactivate">
    `POST /v1/kill-switches/kill-switch-payments/deactivate`
  </Step>
  <Step title="Monitor">
    Confirm normal payment flow resumes via audit log.
  </Step>
</Steps>

### Scenario 2: Agent misbehavior

1. Alert: agent executing unintended bulk operations
2. Activate agent-specific kill switch (conditions match `agent_id`)
3. Other agents continue operating normally
4. Fix agent configuration/logic
5. Deactivate kill switch

## Error responses

| Status | Meaning | Action |
|--------|---------|--------|
| 404 | Rule not found | Check rule name matches policy |
| 400 | Not a KILL_SWITCH rule | Only KILL_SWITCH rules can be toggled via this API |
| 400 | Already in state | Kill switch already active/inactive |
| 403 | Insufficient scope | Use an API key with `admin` scope |
| 404 | No active policy | Create a policy first via `POST /v1/policies` |

## Policy design tips

<Warning>
Always pre-create kill switches with `lifecycle_stage: disabled` so they are ready to activate during incidents. Do not try to write new policy rules during an emergency.
</Warning>

- Name kill switches descriptively: `kill-switch-{scope}` (e.g., `kill-switch-all-payments`, `kill-switch-agent-bot-1`)
- A matching `KILL_SWITCH` rule wins over every other decision whatever its priority; priority orders kill switches among themselves
- Use specific conditions to limit blast radius (tool-specific, agent-specific)
- Document which kill switches exist and what they control
- Test kill switch activation/deactivation as part of incident response drills
