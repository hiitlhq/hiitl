Copy-paste policy patterns for common scenarios. Customize thresholds and deploy.

Load a policy with `HIITL(policy_path="policy.yaml", mode="RESPECT_POLICY")` to enforce it. Under `RESPECT_POLICY`, an action no rule matches is blocked with `NO_MATCHING_RULE`, so a policy needs `ALLOW` rules for the calls that should proceed. Under the default mode, `OBSERVE_ALL`, a decision other than `ALLOW` or `SANDBOX` comes back as `OBSERVE`, with the rule's decision in `would_be`.

Every rule needs a `description`. A rule is active unless its `lifecycle_stage` says otherwise (`disabled`, for example).

## Payment approval workflows

### Simple amount threshold

Require approval for payments over $500. Auto-approve below.

```yaml
name: "payments"
version: "v1.0.0"
description: "Simple amount threshold"
scope:
  org_id: "org_devlocal0000000000"
  environment: "dev"
rules:
  - name: "require-approval-high-value"
    description: "Require finance approval for payments over $500"
    priority: 100
    conditions:
      all_of:
        - field: "action"
          operator: "equals"
          value: "process_payment"
        - field: "parameters.amount"
          operator: "greater_than"
          value: 500
    decision: "REQUIRE_APPROVAL"
    reason_code: "HIGH_VALUE_PAYMENT"
    metadata:
      sla_hours: 4
      reviewer_role: "finance_approver"

  - name: "allow-low-value-payments"
    description: "Allow payments up to $500"
    priority: 1
    conditions:
      all_of:
        - field: "action"
          operator: "equals"
          value: "process_payment"
    decision: "ALLOW"
    reason_code: "LOW_VALUE_PAYMENT"
```

## Rate limiting

A rate limit is a windowed `RATE_LIMIT` rule: `decision: "RATE_LIMIT"` with `rate_limit: {limit, window_seconds, scope}`. A policy set's `metadata.rate_limits` is a shorthand that is compiled to such rules when the policy loads; each entry applies to every action the set evaluates. Either way, the limiter runs after evaluation and counts only calls that come back `ALLOW`, in either mode. The call past the limit comes back `RATE_LIMIT` with `allowed` false.

### Per-agent rate limit

```yaml
policy_set:
  name: "agent-rate-limited"
  version: "v1.0.0"
  description: "Per-agent rate limit"
  scope:
    org_id: "org_devlocal0000000000"
    environment: "dev"

  metadata:
    rate_limits:
      - scope: "agent_id"
        window: "hour"
        limit: 100

  rules:
    - name: "allow-payments"
      description: "Allow payments"
      priority: 1
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
      decision: "ALLOW"
      reason_code: "PAYMENT_ALLOWED"
```

When an action is ALLOW'd by the rules, the rate limiter checks whether the agent already has 100 allowed actions in the last hour. If so, the decision is overridden to `RATE_LIMIT`.

The same limit as a rule, which can also carry conditions of its own:

```yaml
name: "agent-rate-limited"
version: "v1.0.0"
description: "Per-agent rate limit"
scope:
  org_id: "org_devlocal0000000000"
  environment: "dev"
rules:
  - name: "rate-limit-payments-per-agent"
    description: "Allow each agent 100 payments per hour"
    priority: 100
    conditions:
      field: "action"
      operator: "equals"
      value: "process_payment"
    decision: "RATE_LIMIT"
    reason_code: "PAYMENT_RATE_LIMIT"
    rate_limit:
      limit: 100
      window_seconds: 3600
      scope: "agent"

  - name: "allow-payments"
    description: "Allow payments"
    priority: 1
    conditions:
      field: "action"
      operator: "equals"
      value: "process_payment"
    decision: "ALLOW"
    reason_code: "PAYMENT_ALLOWED"
```

### Multiple simultaneous limits

Apply both per-agent and org-wide limits. The first exceeded limit wins.

```yaml
metadata:
  rate_limits:
    - scope: "agent_id"
      window: "minute"
      limit: 60
    - scope: "org"
      window: "hour"
      limit: 5000
```

## Kill switches

Kill switches are regular policy rules with `decision: "KILL_SWITCH"`. A matching active kill switch wins over every other decision, whatever its priority. Set `lifecycle_stage: disabled` by default and set it to `active` during incidents. Add these rules to a policy's `rules:` list.

### Emergency payment stop

```yaml
- name: "kill-switch-all-payments"
  description: "Stop all payments during an incident"
  lifecycle_stage: disabled
  priority: 1000
  conditions:
    all_of:
      - field: "action"
        operator: "equals"
        value: "process_payment"
  decision: "KILL_SWITCH"
  reason_code: "KILL_SWITCH_PAYMENTS_ACTIVE"
```

### Stop a specific agent

```yaml
- name: "kill-switch-agent-123"
  description: "Stop every action from agent-123"
  lifecycle_stage: disabled
  priority: 1000
  conditions:
    all_of:
      - field: "agent_id"
        operator: "equals"
        value: "agent-123"
  decision: "KILL_SWITCH"
  reason_code: "AGENT_SUSPENDED"
```

See the [Kill Switch Runbook](/patterns/kill-switch-runbook) for operational procedures.

## Permission escalation

Add these rules to a policy's `rules:` list.

### Require approval for admin grants

```yaml
- name: "require-approval-admin-grants"
  description: "Require security team approval for admin-level grants"
  priority: 200
  conditions:
    all_of:
      - field: "action"
        operator: "equals"
        value: "grant_access"
      - field: "parameters.role"
        operator: "in"
        value: ["admin", "superuser", "root"]
  decision: "REQUIRE_APPROVAL"
  reason_code: "ADMIN_PERMISSION_GRANT"
  metadata:
    sla_hours: 2
    reviewer_role: "security_team"
```

### Restrict PII access to trusted agents

```yaml
- name: "block-pii-from-untrusted-agents"
  description: "Block actions on PII from agents outside the trusted list"
  priority: 900
  conditions:
    all_of:
      - field: "sensitivity"
        operator: "contains"
        value: "pii"
      - field: "agent_id"
        operator: "not_in"
        value: ["customer-service-agent", "compliance-agent"]
  decision: "BLOCK"
  reason_code: "PII_ACCESS_RESTRICTED"
```

## Environment-based controls

Add these rules to a policy's `rules:` list.

### Sandbox everything in dev

```yaml
- name: "sandbox-all-in-dev"
  description: "Sandbox every action in dev"
  priority: 800
  conditions:
    all_of:
      - field: "environment"
        operator: "equals"
        value: "dev"
  decision: "SANDBOX"
  reason_code: "DEV_ENVIRONMENT_SANDBOX"
```

Its priority puts it above the approval and allow rules in this cookbook. `BLOCK` and `KILL_SWITCH` rules still win in dev.

### Block irreversible actions in dev

```yaml
- name: "block-irreversible-in-dev"
  description: "Block irreversible actions in dev"
  priority: 900
  conditions:
    all_of:
      - field: "environment"
        operator: "equals"
        value: "dev"
      - field: "sensitivity"
        operator: "contains"
        value: "irreversible"
  decision: "BLOCK"
  reason_code: "IRREVERSIBLE_BLOCKED_IN_DEV"
```

## Comprehensive example

A complete payment policy with all layers.

```yaml
policy_set:
  name: "comprehensive-payment-policy"
  version: "v2.0.0"
  description: "Comprehensive example"
  scope:
    org_id: "org_devlocal0000000000"
    environment: "dev"

  metadata:
    rate_limits:
      - scope: "agent_id"
        window: "hour"
        limit: 100

  rules:
    # Layer 1: Kill switch (priority 1000)
    - name: "kill-switch-all-payments"
      description: "Stop all payments during an incident"
      lifecycle_stage: disabled
      priority: 1000
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
      decision: "KILL_SWITCH"
      reason_code: "PAYMENTS_KILL_SWITCH_ACTIVE"

    # Layer 2: Block suspended agents (priority 900)
    - name: "block-suspended-agents"
      description: "Block payments from suspended agents"
      priority: 900
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
          - field: "agent_id"
            operator: "in"
            value: []   # add the IDs of suspended agents
      decision: "BLOCK"
      reason_code: "AGENT_SUSPENDED"

    # Layer 3: Approval for high-value (priority 100)
    - name: "require-approval-high-value"
      description: "Require finance approval for payments over $1,000"
      priority: 100
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
          - field: "parameters.amount"
            operator: "greater_than"
            value: 1000
      decision: "REQUIRE_APPROVAL"
      reason_code: "HIGH_VALUE_PAYMENT"
      metadata:
        sla_hours: 4
        reviewer_role: "finance_approver"

    # Layer 4: Default allow (priority 1)
    - name: "allow-standard-payments"
      description: "Allow payments up to $1,000"
      priority: 1
      conditions:
        all_of:
          - field: "action"
            operator: "equals"
            value: "process_payment"
      decision: "ALLOW"
      reason_code: "STANDARD_PAYMENT"
```

Precedence is deny-wins: an active kill switch first, then blocks, then the other rules by priority (here the approval, then the allow). Only ALLOW decisions are counted against rate limits.

## Priority guide

| Priority range | Category | Examples |
|----------------|----------|----------|
| 1000+ | Kill switches | Emergency stop |
| 900 - 999 | Deny / Block | Suspended agents, blocked tools |
| 100 - 399 | Threshold checks | Amount limits, approval workflows |
| 1 - 99 | Allow rules | Default allow, standard operations |

A matching kill switch or `BLOCK` rule wins over every other decision whatever its priority; priority orders rules within each class. These ranges keep a policy readable.

<Note>
A windowed `RATE_LIMIT` rule meters calls rather than deciding them, so its priority does not compete with the rules above. `metadata.rate_limits` compiles to such rules.
</Note>

## Policy deployment workflow

1. **Write** -- author policy as YAML
2. **Test locally** -- validate with synthetic data in local mode
3. **Review** -- policy is code, use Git pull requests
4. **Deploy to dev** -- test with real agents
5. **Deploy to stage** -- validate with production-like traffic
6. **Deploy to prod** -- monitor audit trail closely
7. **Iterate** -- adjust based on observed decisions
